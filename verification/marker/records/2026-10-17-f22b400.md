## Which engine sees the marker

`klt drc` has three usable paths; they are different decks:

1. **curated** (`--deck sky130`): no rule references any `areaid.*` layer other than
   `areaid_re.ongrid.1`; `klt deck rules` output has 0 matches for `sram|core|areaid.(sc|ce|sl)`. Marker-blind.
2. **`sky130A.lydrc`**: references 81/2 in a handful of well/implant rules; **no** li, licon, mcon or poly rule is switched by it.
3. **`sky130A_mr.drc`**: switches li (li.1/li.3 outside vs li.7/li.8 inside), licon, mcon, poly, diff/tap, nsdm/psdm, via and others on 81/2. Only this one implements core/periphery rule switching for the cells that matter here.

Note: `klt drc --engine klayout ...` reports `coverage_unknown` (exit 4) for every
zero-finding run, so "0" below means "no violation reported", never "proven clean".
Evidence that the mr deck really executed: the stripped-marker control (47).

## Verdicts (stated plainly)

- **Curated sky130 deck: wrong for marker-bearing cells, by omission.** It
  ignores the marker, so the foundry bitcell fails with 101 violations even
  with its marker, and a logic cell gets the same checks inside and outside it.
  The failure direction is false violations, not hidden ones. It does not
  silently apply the wrong rule set; it applies one rule set everywhere.
- **`sky130A.lydrc`: unspecified for this purpose.** It knows the marker for a few rules and not for li/licon/mcon, so the foundry cell fails (56) with its marker. Do not use it to sign off marker-bearing geometry.
- **`sky130A_mr.drc`: correct inside and outside, per-shape at the edge, with one seam hole.** Rules switch per drawn shape by whether it lies outside, inside or crosses the marker. Inside the marker the **strict logic rules are not enforced** (probe: 3 violations hidden, 0 reported). A shape that crosses the edge is checked against the strict width/spacing rule as a whole *and* its inside part against the core width rule (li.8 slivers). **Spacing between a core-side shape and a periphery-side shape across the edge is checked by neither li.3 nor li.7** (probe, edge in the gap: 0.15 um spacing reported clean). This hole is observed for li only; other layers were not probed.
- The silent-wrong-rule-set risk is real in one direction: **a logic-rule cell
  placed under 81/2 is checked to the relaxed rules and passes with violations the
  logic rules would reject.**

## Answers for the spec

1. **Does the logic-rule bitcell need the marker?** For DRC legality, no: it is checked against, and must satisfy, the ordinary (periphery) rules with no marker. Putting it under 81/2 adds nothing for DRC and removes li.1/li.3 enforcement (and others), so it would let real logic-rule violations through. Whether the foundry's own acceptance or other flows (LVS, extraction, fill) need or react to the marker was not tested here. Keep any marker use an explicit, recorded decision in the spec issue.
2. **What the array/periphery seam must satisfy** (mr deck behaviour, li probed): keep the 81/2 boundary in li-free space so no li shape crosses it (crossing shapes get both strict width and li.8); put li on either side at >= 0.17 um spacing by construction, because neither deck checks it across the edge; note the foundry cell's own marker is inset 0.315 um at left and right and flush at top and bottom, so how markers of tiled cells join (and whether a gap opens between them) must be checked on the real array, which was not tiled here. Review the seam by a purpose-built check rather than trusting a green DRC. Layers other than li remain to be probed.
3. **Which deck signs off a marker-bearing array**: only `sky130A_mr.drc` (with `--deck-var feol=true --deck-var beol=true --deck-var thr=1`), plus a stripped-marker negative control per run so a silent zero-rule execution cannot pass as clean. The curated deck cannot.

## Upstream tool gaps (filed at 2AMLogic/klayout-tools)

- 2AMLogic/klayout-tools#3815: no way to tell whether a deck's rules are conditioned on an area-marker layer; curated sky130 deck is marker-blind without saying so.
- 2AMLogic/klayout-tools#3816: PDK-shipped sibling decks and their required `-rd` globals are undiscoverable (`--pdk` picks only `sky130A.lydrc`).
- Already known and closed upstream, reproduced here: #1302 (missing deck vars cause a silent zero-rule run; hit again until `--deck-var` was supplied), #2697 (zero-finding external-deck runs are never labelled `clean`).
